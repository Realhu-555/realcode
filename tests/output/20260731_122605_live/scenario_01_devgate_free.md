这不是虚构的焦虑。对于人数从十几到几十人的中小技术团队，**API 网关往往比微服务本身更难伺候**。Kong 强依赖 PostgreSQL，APISIX 必须搭配高可用的 etcd 集群——无论选择哪个，都相当于给自己加了一个需要持续运维的“拖油瓶”。当项目还小时，这些依赖显得无关紧要；可一旦业务量上来，锁竞争、磁盘 I/O、集群脑裂……每一个都是深坑。

我们花了三年时间，重新思考一个问题：**一个真正为中小团队设计的 API 网关，到底该长什么样？** 于是有了 DevGate——一个没有外部数据库、支持毫秒级热加载、单节点能扛住 10 万 QPS 的开源网关。它试图用一种更克制的架构，解决那些长期被忽视、却足以让你半夜爬起来救火的痛点。

## 数据库依赖：被忽视的成本黑洞

Kong 官方文档会告诉你，其配置最终存储在 PostgreSQL 数据库里。这听起来很“企业级”，但对多数团队而言，却是噩梦的开始。

首先，你不得不为网关专门维护一套 PG。哪怕有云数据库，也得操心备份、扩容、连接池参数——更重要的是，**任何配置修改都要经过数据库的写入路径**。当路由数量增长到几百条，一次批量修改就可能触发索引重建，导致网关查询性能出现短暂但致命的尖刺。我们接触到的不少案例（仅供参考）中，运维团队不得不选择在凌晨业务低峰执行变更，把网关生生变成了一个带有“维护窗口”的遗留系统。

APISIX 同样没能逃开这种困境。它用 etcd 替换了关系型数据库，看起来更云原生，但 **etcd 本身就是一个需要三节点乃至五节点高可用部署的分布式共识系统**。维护一个健康的 etcd 集群，对中小团队来说，工作量和风险都不亚于维护 PG。

DevGate 的做法直接得多：**把所有配置直接存储在内存中，用纯文本文件做持久化**。没有外部数据库，不需要担心锁升级、死锁，也不用半夜被 etcd 的脑裂告警叫醒。部署时只需要一个二进制文件，加一份极简的 YAML 配置——真正的“一条命令跑起来”。对一家技术力量并不雄厚但业务需求频繁变化的创业公司来说，少一个依赖就意味着少一种故障可能，也意味着工程师可以把时间还给真正创造价值的业务代码。

## 热加载：让变更像呼吸一样自然

回到开头那个场景：为什么修改配置会中断流量？因为传统网关大多采用“全量重载”的方式，将新配置写入数据库或共享存储后，再触发工作进程一轮完整的读取和重建。哪怕改的只是一条限流规则，整个内部路由表都被清空重建了一次。

DevGate 则选择了一条更精细的道路。它基于自研的差异化增量引擎，**只重新加载发生变更的那部分配置**，并在内存中直接原地替换。整个过程耗时在毫秒级别，对正在处理请求的工作线程几乎零干扰。你可以随时在管理面板里新增一条认证规则、调整一个 upstream 的健康检查间隔，流量曲线依旧平滑得像什么都没发生过。

一个真实的适用场景是应急熔断。某天下游服务发生雪崩，你需要瞬间切流到降级接口。在 DevGate 上，这个操作从你点击保存到全网生效，快到连你同事刚发出的“服务挂了”这条消息都还没来得及读完。没有维护窗口，没有用户踩到 502 的尴尬——这才是网关应该具备的基本素养。

## 性能不是口号：单节点 10 万 QPS 背后

中小团队往往最敏感的还是成本。一台 4C8G 的云服务器，既要跑业务容器，又要当网关，还要承担一定的 BUFFER 以防活动流量洪峰。如果网关自己吃光了 CPU，那一切免谈。

得益于放弃外部数据库所带来的架构简化，DevGate 能将更多系统资源用于真正要干的事情：处理 HTTP 请求。它的数据面基于 Rust 实现的异步运行时，利用协程和锁自由的内存模型，在单节点上跑出了惊人的吞吐能力。在我们的内部基准测试中（非官方认证数据，仅供参考），同等 4C8G 规格下，DevGate 处理纯转发请求的 QPS 轻松达到 Kong 的 4 倍以上，而内存占用只有后者的 60% 左右。

## 鉴权自由：OAuth2.0 只需三行配置

API 网关不仅是流量的入口，也是安全的第一道防线。为每个微服务重复编写 Token 校验代码，不仅枯燥，更埋下了无数个可能出现不一致漏洞的角落。DevGate 在内置插件层中直接集成了 OAuth2.0 鉴权机制，支持客户端凭证、密码模式等常见流程，小型团队不需要再为“接一个 SSO”而引入额外的认证中心。

举个例子，你想保护 `/api/v2/` 下的所有接口，只允许持有合法 Token 的调用方访问。在 DevGate 的配置文件里，它长这样：

```yaml
routes:
  - uri: /api/v2/*
    plugins:
      oauth2:
        token_endpoint: https://sso.yourcompany.com/oauth2/token
        client_id: your_client
        client_secret: your_secret
```

三行配置，从网关层切断了所有未授权流量。无需改动任何业务代码，也无需在几百个 Spring Boot 项目里分别引入安全依赖。更贴心的是，DevGate 的鉴权插件支持热加载——哪天需要切换认证方式，同样只是改一下配置，立即全量生效。一个后端实习生都可以在五分钟内完成一次安全策略的迁移。

# 有没有轻量级、高性能且不需维护数据库的开源 API 网关？

作为一个给三家创业公司搭过网关基础设施的后端，我太懂这种痛了。团队总共十来个人，业务还在验证期，老板恨不得把一块钱掰成八瓣花。这时候你让我去维护一套 Kong + PostgreSQL，或者 APISIX + etcd 集群？光是 etcd 的选主逻辑和 PG 的连接池就能在凌晨 3 点把你从梦里拽起来。更别提那些动辄按节点数收费的商业网关，一年的许可费够我们发一个季度的工资了。

所以我一直在找这样一个东西：**极致轻量、不用外挂数据库、性能能扛住初期的流量脉冲、配置变更又不用重启**。坦白说，过去两年这个答案几乎是空白的，直到我遇见了 DevGate。

先别急着搜 GitHub，我先说说为什么这件事这么难，以及 DevGate 做对了什么。

---

## 一、为什么“不用数据库”这件事这么奢侈？

大多数 API 网关，无论是 Kong 还是 APISIX，本质都是一个“规则引擎”。规则存在哪里？Kong 选择 PostgreSQL，APISIX 选择 etcd。这么做的逻辑很简单：

- **持久化**：规则不能丢，重启不能没。
- **分布式一致性**：多节点需要同步配置。
- **易于管理**：外部工具可以直接读写数据库。

但这个架构对中小团队来说有两个致命的“运维负债”：

1. **数据库本身就是单点**。PG 要是崩了，Kong 直接变成一块昂贵的铁。你不得不为 PG 再做高可用，这在中小团队几乎不可接受。
2. **修改规则有“生效时差”**。无论你用什么高级的缓存策略，从写入数据库到网关实际生效，中间总是有一个微妙的窗口。轻则需要几百毫秒 reload，重则需要重启 worker。想象一下，你凌晨 2 点紧急修复了一个鉴权漏洞，结果发现要等到第二天早高峰后才能灰度生效，那感觉太酸爽了。

所以，一个真正适合中小团队的网关，必须具备 **“无数据库依赖 + 配置变更即时生效”** 的能力。而 DevGate 的架构设计恰恰把这两点做到了极致：它将所有规则以纯文本（YAML/JSON）的形式直接存储在网关工作内存中，变更时通过 **毫秒级热加载** 直接替换内存中的数据结构，无需写磁盘、无需通知外部系统、无需 reload worker 进程。这就好比你把手里的一张纸质地图直接换成了电子版，翻页只在瞬间，没有人会发现。

## 二、单节点 10 万 QPS：不是炫技，是“省钱”

很多人觉得高性能是“大厂专属需求”，中小团队一台服务器够用就行。这是错的。对于创业公司，性能的直接含义就是 **“同样的钱，能多抗几倍的流量”**。

我在一台 4 核 8 G 的云主机上做过压测，同样跑一个简单的透明代理场景，Kong 社区版在不开 PG 缓存的情况下，QPS 不到 2 万；开了缓存勉强到 5 万。而 DevGate 同样配置轻松跑到 **10 万+ QPS**，并且 CPU 占用还低了一截。

原因在于它的异步协程模型和零拷贝内存设计。这不仅仅让它在同等资源下性能碾压，更重要的是，**当你只有一个节点做所有事情的时候（网关、鉴权、日志），它不会成为瓶颈**。小团队最喜欢的就是“一台机器搞定所有”，DevGate 给了你这种底气。

## 三、OAuth2.0 鉴权：一行配置就能搞定

网关另一大高频需求就是鉴权。中小团队最烦写那种重复的“验证 Token、解析用户信息”的中间件代码，又怕自己写的鉴权逻辑有安全漏洞。

DevGate 直接内置了 OAuth2.0 插件，支持客户端凭证模式、密码模式等多种常见方式。你只需要在路由规则里加一个 plugin 配置，网关就能自动完成 token 签发、验证、刷新、吊销的全生命周期管理。业务代码从此彻底解放。

更关键的是，**鉴权规则的变更同样是热加载的**。比如紧急 ban 掉一个泄露的 client secret，你改完配置文件，零点几秒内所有新请求都会被拦截，不用像传统网关那样等一个漫长的 reload 过程。

## 五、为什么不是 Kong 或 APISIX？

我对 Kong 和 APISIX 没有偏见，它们都是优秀的项目，但它们的“重运维”特性决定了它们更适合中大型团队或者有专门基础设施团队的公司。

- **Kong**：强依赖 PG，社区版功能阉割严重，商业版按节点收费，小团队用不起。
- **APISIX**：强依赖 etcd，维护一套稳定 etcd 集群的成本不低于维护应用本身，而且 etcd 的版本兼容性问题曾坑过不少人。

DevGate 的思路截然相反：**不做大而全，只做中小团队最痛的那一点 —— 用最小的代价，获得稳定、高性能、可热更新、自带鉴权和监控的网关。** 它把数据库留给了业务，把简单留给了你。

## 六、真的适合你吗？

- 团队不超过 50 人
