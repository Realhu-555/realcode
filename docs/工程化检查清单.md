# 工程化检查清单 — Agent / RAG 项目交付模板

> 用途：做新功能、新模块、新 Agent 前/后，按本清单过一遍，把「demo 思维」变成「工程思维」。
> 用法：功能设计期过「5 问」；实现期对照 8 维度逐项打勾；出问题用「事故复盘模板」固化规则。
> 版本：v1.0 ｜ 日期：2026-08-26 ｜ 示例取自本项目（GIS 智能操作助手）。

---

## 0. 快速 5 问（任何功能开工前必问）

- [ ] 它挂了，我怎么第一时间知道？（日志 / 状态码 / 告警 / 前端错误提示）
- [ ] 它超限了会怎样？（步数 / 时间 / 重试 / 资源上限）
- [ ] 我凭什么说它「对了」？（测试 / 断言 / 评测锚点 / 验收标准）
- [ ] 三个月后的我或别人能接手吗？（文档 / 注释 / 接口清晰 / 命名规范）
- [ ] 每跑一次要花多少钱？（token / 请求数 / 外部调用 / 存储）

**任一问题答不上来 → 先补设计再写代码。**

## 1. 八维度检查（实现期逐项打勾）

### 1.1 确定性优先（能规则化的不让 LLM 判）

- [ ] 校验/判断是否可写成纯函数（非 LLM）？
- [ ] LLM 输出是否过了规则断言（数字核对 / 格式校验 / 枚举白名单）？
- [ ] 关键错误是否可复现、可单测？

> 本项目示例：`validate_final_numbers` 用规则抓「12.6 vs 126 万亿」量级错；`checker.check_outputs` 做文件级校验。

### 1.2 可观测（一切可追踪）

- [ ] 关键步骤是否落日志/轨迹（输入、输出、耗时）？
- [ ] 运行结果是否可回放（轨迹文件 / 会话记录）？
- [ ] 错误是否带上下文（哪一步、什么参数、返回什么）？

> 本项目示例：`trajectory`（工具名/参数/返回）落 `data/gis_traces/`；`agent_logger` 记录每次 tool_call。

### 1.3 可控（所有循环有上限和出口）

- [ ] 循环/重试是否有硬上限？
- [ ] 超时/挂起是否有兜底（默认拒绝 / 超时终止）？
- [ ] 是否有手动中断/停止入口？

> 本项目示例：`max_steps=12`、`max_check_retries=3`、审批 `APPROVAL_TTL_SECONDS=60` 超时默认拒绝。

### 1.4 可评测（没有数字就没有改进）

- [ ] 是否定义了量化指标（通过率 / 耗时 / 成本 / 覆盖率）？
- [ ] 是否有自动化评测或验收锚点（能复现的失败案例）？
- [ ] 指标是否进报告（pass-rate / fail-reasons）？

> 本项目示例：benchmark L1 引擎级断言 + L2 真实任务；审核通过率；锚点用例「12.6 vs 126 必须 FAIL」。

### 1.5 可维护（改配置不改代码）

- [ ] 新增能力是否表驱动 / 注册表 / 配置化，而非堆 if-else？
- [ ] 核心接口是否有抽象层（换实现不动调用方）？
- [ ] 是否向后兼容（旧数据/旧调用不崩）？

> 本项目示例：`TOOL_SCHEMAS` 一处定义三端生效；双引擎 `GIS_ENGINE` 切换；`models.yaml` 注册表驱动。

### 1.6 成本意识（每次调用都算钱）

- [ ] 上下文是否做了窗口/摘要压缩？
- [ ] 昂贵的 LLM 调用是否只在必要时触发？
- [ ] 是否记录成本（每次调用的 token / 价格）？

> 本项目示例：滚动摘要 80% 阈值提前压缩；L2 审核仅在有产物且 L1 非全 PASS 时跑；`cost_tracker` 记成本。

### 1.7 安全边界（默认拒绝、最小权限）

- [ ] 危险操作是否需人工审批 / 二次确认？
- [ ] 文件/路径/URL 是否有白名单与净化（防穿越/注入）？
- [ ] 密钥/敏感信息是否不回显、不入库明文？

> 本项目示例：`ApprovalGate` 三档权限；路径白名单 + 文件名净化；API key 只返回 `has_key`。

### 1.8 演进思维（先跑通再迭代）

- [ ] 是否先小步跑通再扩展（MVP → 增强）？
- [ ] 接口变更是否有兼容层或版本字段？
- [ ] 是否有「未来替换」的预留点（接口/扩展位）？

> 本项目示例：脚本生成 → 工具调用演进；`done` 事件新增字段向后兼容；`execute_subtask` 子任务预留。

## 2. 事故复盘模板（把踩坑固化成规则）

每次线上/测试出问题，按这个模板记录一次，积累成你自己的「规则库」：

```markdown
## 事故：<一句话标题>
- 现象：<用户/系统看到了什么>
- 根因：<为什么发生>
- 修复：<怎么改的>
- 抽象规则：<能推广到其他场景的一条规则>
- 防复发：<测试/断言/检查项>
```

**本项目已固化的 4 条规则（可直接照抄进你的规则库）**

1. LLM 输出必须过规则校验
   - 事故：finish 汇报把「126 万亿」写成「12.6 万亿」；
   - 规则：任何 LLM 生成的关键数字/结论都要有工具返回或产物可溯源。
2. 危险操作默认值必须「拒绝」
   - 事故：审批超时默认放行，对危险操作是反向的；
   - 规则：安全相关的默认值一律取最保守（reject / readonly）。
3. 消息结构要防窗口切断
   - 事故：`role=tool` 无前导 `tool_calls` 导致 400；
   - 规则：裁剪历史窗口时要对齐到消息边界，做兼容处理。
4. 环境问题要记 workaround
   - 事故：pytest 临时目录 ACL 损坏导致批量 PermissionError；
   - 规则：测试命令固定 `--basetemp`，环境类问题记录解决方案而非反复排查。

## 3. 交付前最终勾选

- [ ] `ruff check` / 格式检查通过

## 4. 一句话总结

> 工程化不是某一步做完，而是每做一个功能都过一遍：**能规则化的不用 LLM、能追踪的必须追踪、能设上限的必须设上限、能量化的必须量化、能配置的不写死、能预留的留好口子。**
