# 面试准备 · 客服 Agent 提示词调优岗（v2 聚焦版）

> 岗位：客服类 Agent 的 prompt 编写 / 流程配置 / 节点调试 / 功能与效果测试 / 调优。
> HR 想听的核心（已确认）：**你做过一个 AI Agent，并且调试过提示词——说清楚你调了什么、回答质量提升在哪、怎么证明提升。**
> 主线：**我是用"失败轨迹驱动"的方法调 prompt 的——先看 Agent 在哪步翻车，再改提示词，再用回归用例证明改好且没改坏别的。**

---

## 1. 60 秒主答案（背熟，面试官一问"调过提示词吗/提升多少"就讲这个）

> 我做过一个工具调用型 AI Agent，提示词调优是我日常就在做的事。我讲两个真实案例，都有 git 记录和测试佐证。
>
> **案例一：任务干完不汇报。** 早期 Agent 长任务执行完会直接结束，没有给用户任何结论。我看了它的运行轨迹定位到是系统提示词里对"收尾"约束不够硬。我改了两处：一是把提示词改成硬规则——"任务全部完成后，最后一步必须调用 finish 收尾并汇报，禁止直接结束"，并且规定汇报必须包含"做了什么 + 具体数字（且数字必须来自工具返回）+ 产物清单"；二是加了兜底——就算模型没遵守，系统也会自动生成一段非空汇报，不让你对着空白发呆。改完后我把它固化成回归断言："任务轨迹最后一步必须是 finish"，整条链路 455 个自动化用例全绿。**结论：我把"会不会好好汇报"从碰运气变成了有规则、有兜底、可回归。**
>
> **案例二：回答里的数字可能与工具结果对不上。** Agent 有时会在最终汇报里写出和工具真实返回不一致的数字（幻觉）。我加了一层"结果审核"：Agent 汇报完，另一个审核环节把汇报里的关键数值和工具返回逐项核对，不一致就打回让 Agent 只重写汇报、不重跑工具，最多两轮。配套写了 236 行测试覆盖"通过 / 发现错误 / 修正 / 拒绝修正"。**结论：回答的"正确性"从靠模型自觉，变成有第二道关卡自动拦截。**
>
> 至于"提升了多少"这个数——我如实说：我项目的自动化正确性有硬指标（455 用例全绿、评测集要求必须收尾才算成功），但"效果提升百分比"这种规模化跑分我还没跑，所以我不给你编的数。**我的做法是可复制的：调每一版 prompt 都留版本、都跑同一回归集、都记轨迹。到贵司第一周，我会拿你们历史对话建一个小标注集先跑出基线，之后每次调 prompt 都用基线前后对比说话。**

## 2. 两个案例的"证据细节"（追问时可展开，全真实）

### 案例 A：强化收尾汇报（git：`d92c04b`，2026-08-25）

## 3. 诚实回答"提升了多少"——三句话框架

1. **我给得出的硬指标**：455 个自动化用例全绿（覆盖工具、审批、审核、记忆、模型配置）；评测口径要求"必须收尾 + 审核通过"才算任务成功——这就是我对"质量"的定义，不用嘴说，用规则。
2. **我没跑出来的数我不编**：规模化成功率/准确率跑分还没做。但我的评测基础设施在（回归集 + 审核通过率记录 + 轨迹留痕），随时能跑出基线。
3. **到岗第一周我就能出第一版基线**：拿你们 50~100 条真实对话标注 5 个指标（意图对错 / FAQ 命中 / 该转人工没转 / 话术合规 / 首答满意），先量化"现在多差"，之后每次调 prompt 用同一批用例看涨跌。**这句话比任何编的数字都加分。**

## 4. 我的提示词调试方法（五步闭环，讲给"流程化"岗位听）

| 步 | 做什么 | 对岗位的话 |
|---|---|---|
| 1 看轨迹 | 让 Agent 干活，看它每一步调什么、哪步翻车 | "调试靠轨迹不靠猜" |
| 2 分类 | 失败=理解错（改 prompt/意图）还是执行错（改工具/节点） | 对应岗位的"节点修正 vs prompt 优化" |
| 3 改一点 | 一次只改一处约束，能落 schema/代码硬校验就不只靠嘴 | 提示词越少靠"自觉"越好 |
| 4 加用例 | 把这次翻车转成一条回归用例 | 对应"按标准流程记录问题" |
| 5 回归 | 全量跑，防止改好 A 弄坏 B | 对应"保障交付质量" |

> 落点：**"这个闭环就是我理解的岗位日常：搭节点、调话术、记录问题、回归反馈。"**

## 6. 预判追问（精简版）

**Q：没做过客服，凭什么？**
> 客服 Agent 内核=意图路由+知识库+话术+转人工+评测。我做的 Agent 覆盖意图路由（工具选择）、知识召回（记忆）、人工接管（审批）、评测闭环；话术部分我研究过（情绪分流/模板化/转人工）。差的只是业务语料，我第一周就能用你们的对话样例把意图清单和话术模板建起来。

**Q：prompt 好不好怎么判断？**
> 不看感觉看行为：同一批任务调前调后对比；能硬约束的（枚举、必填、格式）用代码校验而不是提示词祈祷。坏 prompt 的典型症状是有时好有时坏——那就说明靠模型自由发挥了。

**Q：改好 A 弄坏 B 怎么办？**
> 每次翻车转成回归用例，全量回归再上线；prompt 留版本可回退。案例 A 后我就把"必须收尾"做成了回归断言，改别的功能再也没弄坏过收尾。

**Q：答非所问 / 幻觉？**
> 三层：入口意图识别+兜底（识别不了就转人工/反问）；回答层能查就查、禁止编造、标不确定；出口内容校验（我案例 B 就是这么做的：第二道审核把数字错误拦下来）。

**Q：长对话聊乱/超上下文？**
> 我最近刚做完 auto-compact（对标 Claude Code）：按模型上下文 85% 触发，把历史压成摘要、保留最近原文、恢复用户关键上下文（订单/进度）。对客服多轮是刚需。
