## 2. 三轮评测记录（2026-09-04）

运行命令：`venv\Scripts\python.exe -m src.gis_toolkit.bench`
报告存档：`data/gis_bench_results/<时间戳>/report.json`

### v1（16:01）—— 基线：功能全对，汇报质量不过关

| 任务 | 完成 | 审核 | 问题 |
|---|---|---|---|
| choropleth | ✅ | ❌ FAIL | final 声称"31 省全部参与分级"，又声称"3 省未着色"，自相矛盾；"3 省"在工具返回中无依据 |
| summarize | ✅ | ✅ | — |
| buffer | ✅ | ✅ | — |
| scatter | ✅ | ✅ | — |

结论：工具层正确率 100%，但**最终汇报的可信度**是短板——数字是否来自工具、表述是否自洽无人把关，这正是 L2 审核存在的意义。

### v2（16:04）—— 第一轮修复：工具回报缺失省名单 + 提示词要求如实披露

改动：
1. `engine.py` choropleth 返回信息带**缺失省份名单**（不只报数量）；
2. `agent.py` SYSTEM_PROMPT 增加规则："若图表/统计工具返回提示存在缺失数据（如无数据省份），必须如实说明缺失情况，不得声称全部覆盖"。

结果：choropleth FAIL → **WARN**（模型已正确列出台湾省/澳门/香港 3 省缺失）；剩余 WARN 是"文件大小/聚合过程在工具返回中无结构化证据"。

### v3（16:07）—— 第二轮修复：工具返回结构化 stats 供审核核验

改动：`engine.py` choropleth 返回增加 `stats` 字段：
`{output, size_bytes, scheme, k, aggregated, missing_provinces}`，让审核器能逐项核验 final 里的数字。

结果：choropleth WARN → **PASS**；全量 4/4 完成 + 4/4 审核通过。

## 3. 这次闭环证明了什么

1. **评测基线能抓到"测试发现不了"的问题**：4 个任务产物全对（传统断言全绿），但汇报与工具事实冲突只有审核层能抓出来；
2. **调优方法有效**：改一点（工具返回证据 + 一条提示词规则）→ 复跑 → 看审核维度变化，两轮从 75% → 100%；
3. **可迁移到客服岗话术场景**：同一套"看失败 → 改提示词/补证据 → 回归"方法，只是把"工具返回"换成"知识库/订单数据"。

| 局限 | 下一步 |

| 指标只有两档 | 增加：平均步数、人工介入率、失败原因分类（理解错/执行错/汇报错） |
